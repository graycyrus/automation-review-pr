## Review: PR #3191 — fix scheduler-gate CPU sampler OOB panic

**What it does**

The app has a background "scheduler gate" that throttles work based on system pressure. Every 30 seconds it samples CPU usage. It was doing this by reusing one long-lived `System` object created once when the process started. On Linux, the `sysinfo` library locks in the number of CPU cores at that first read. If the host later gains cores (cloud VMs re-balancing vCPUs, CPU hotplug — the affected host runs a Proxmox kernel), the library tries to read a core slot that no longer fits its original list and **crashes** — `index out of bounds`. One production host hit this on *every* tick, producing 10,802 Sentry crash reports, and its CPU-throttle signal was silently falling back to a neutral default (so the gate was effectively blind there).

The fix: build a brand-new `System` inside each `sample_cpu()` call instead of holding one for the process lifetime. Each call now sizes its core list to the *current* core count, so the index can't run off the end. The two-refresh delta logic (needed to compute a usage percentage) is unchanged. Removes the now-unused `Lazy`/`Mutex` statics. Adds three unit tests asserting the result is finite, in 0–100 range, and panic-free.

**Safety & Breaking concerns — Breaking risk: Zero**

- **Security:** None. No input handling, auth, or data paths touched. Reads `/proc/stat` via the same library as before.
- **Breaking changes:** None. Output contract is identical — still consumes only `global_cpu_usage()`. Per-core state was never read, so dropping it across calls is genuinely free (PR's claim checks out against the diff). Removed imports (`Lazy`, `Mutex`) are confirmed unused after the change.
- **Edge cases:** The fix shrinks the panic window from "permanent after any boot-time core drift" to "core count changes within the ~250ms intra-call window" (transient, rare) — a strict improvement, not a full elimination. Honestly disclosed in the PR. A follow-up to bump `sysinfo` past 0.33 is noted.
- **Production blast radius:** Negligible cost — one extra `System::new()` + one `/proc/stat` parse per 30s tick. The existing `spawn_blocking` unwind-catch in `gate.rs` remains as a backstop. No behavior change at all on fixed-core hosts.

One minor note: the lib still does a `thread::sleep(~250ms)` per sample, but that's pre-existing behavior on a blocking task, not introduced here.

**Bottom line**

Safe to merge — a tightly-scoped, well-documented bug fix with zero behavior change for normal hosts, removing a high-volume crash and restoring a broken signal; already approved by CodeRabbit and graycyrus.
